## 1. WHY THIS PROCESS CONTROL EXISTS

In the development lifecycle of this platform, automated evaluation tooling produced false-positive "VERIFIED" claims on two distinct occasions:

1. **Incident 1 (Phase 9 Audit)**: A high-density automated test script asserted 574/574 tests passing, yet core user flows (Dashboard CTA, month selector, settings mutation) were found non-functional upon human inspection.
2. **Incident 2 (Phase 10B Initial Evidence Harvest)**: The initial read-only evidence collector queried PostgreSQL and reported `Stripe = VERIFIED-EXTERNAL` because it found 5 rows in `billing_webhook_events`. In reality, these rows were legacy artifacts generated by Phase 8B's synthetic test script (`verify-phase8b-stripe.ts`), and the Stripe CLI was not even installed on the host machine.

---

## 2. THE THREE MANDATORY INTEGRITY RULES

### Rule 1: Evidence Tooling Is A Claim, Not Ground Truth
Any output produced by an automated script (e.g. `verify-phase10-external.ts` or `run-phase10b.ps1`) is itself treated as a claim subject to code audit. It must never be accepted as proof until its logic and provenance guards are verified.

### Rule 2: Freshness Window & Causal Provenance Are Mandatory
A database record alone is insufficient to grant `VERIFIED-EXTERNAL`. To qualify:
- **Freshness**: The record timestamp must fall within the active session window ($\le 60\text{ minutes}$).
- **Causal Link**: The record must be directly traceable to an action executed in that same session (e.g. an active Stripe CLI process, an active live FFmpeg process, or a human OAuth browser redirect).
- **Provenance Separation**: Historical or synthetic test rows must be categorized as `STALE-HISTORICAL` or `CLI_NOT_RUN_THIS_SESSION` and permanently barred from conferring external production verification.

### Rule 3: No Retroactive Upgrades Without Fresh Evidence
Never upgrade a subsystem's status in `MASTER_CURRENT_STATE.md`, `CRITICAL_GAPS.md`, or `FEATURE_MATRIX.md` based on uncorroborated text or stale historical records.

## 3. ONGOING MONITORING CADENCE (POST-CONDITIONAL-GO)

With the successful verification of YouTube RTMP live broadcasting (`VERIFIED-EXTERNAL`), the system transitions to a lightweight monitoring posture:

### A. Lightweight Periodic Self-Check (5 Minutes)
1. Run:
   ```powershell
   powershell -ExecutionPolicy Bypass -File scripts/run-phase10b.ps1
   ```
2. Confirm `cloud_autonomy` reports an active heartbeat from the worker.
3. Confirm zero secret leaks in `dist/` or public assets.

### B. When to Re-open a Full Verification Round
A full multi-point audit cycle is justified ONLY upon:
- Major core dependency upgrades (`@supabase/supabase-js`, FFmpeg binary bumps).
- Any modifications to Stripe webhook handlers, billing schemas, or RLS policies.
- Addition of new OAuth providers or video destination endpoints.
- Any incident report of live stream interruption in production.

### C. What Does NOT Require Re-verification
- Routine UI copy updates, design token styling, and layout simplifications.
- Non-billing, non-streaming bug fixes.
